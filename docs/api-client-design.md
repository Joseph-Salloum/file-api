# API Client Design

## 1. Proposed Fields

|     Field     | PostgreSQL Type | Nullable | Default | Constraints |               Reason                |
|      id       |      UUID       |    No    |   Non   | Primary Key |     identifying each API-client     |
|     name      |  VARCHAR(255)   |    No    |   Non   |     Non     |    makes client management easier   |
|  is_enabled   |     BOOLEAN     |    No    |  True   |     Non     |  determine which client is active   |
|   created_at  |      TSWTZ      |    No    | curr ts |     Non     | record of when a client was created |

## 2. Design Decisions

### 2.1 API Key Storage
How will API keys be stored securely?
API keys will be stored in a separate table called api_keys

### 2.2 Authentication
How will the system identify a client from an incoming API key?
the API key will have this format: fa_<key_id>.<random_secret>, I will extract the key id and fetch it from the api_keys table, make sure the secret keys matches, then identify the api_client from an api_client_id column in the api_keys table

### 2.3 Client Deactivation
How will disabling a client affect its access?
I will check for the is_enabled column of the client, if it was false then I will return 401 unauthorized even if the key is valid and active and not expired

### 2.4 Client Isolation
How will the authenticated client identity be connected to file ownership?
every file in the files table reference the API-client that owns it, I will check if the authenticated client id matches the the file owner id

## 3. Assumptions

- I will use UUID Version 7: Time-Ordered Database Keys for the id field in this table and will be generated by the java code.
