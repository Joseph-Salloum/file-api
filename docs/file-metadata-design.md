
# File Metadata Design

## 1. Proposed Fields

|       Field       | PostgreSQL Type | Nullable | Default | Constraints |            Reason              |
|        id         |      UUID       |    No    |   Non   | Primary Key |     identifying each file      |
|     file_name     |  VARCHAR(255)   |    No    |   Non   |     Non     |     the name of each file      |
|  file_size_bytes  |     BIGINT      |    No    |   Non   |  Check >= 0 |      file size in Bytes        |
|     mime_type     |  VARCHAR(255)   |    No    |   Non   |     Non     |           MIME type            |
| storage_configuration_id |      UUID       |    No    |   Non   | Foreign Key |  reference the storage config  |
|    storage_key    |  VARCHAR(1024)  |    No    |   N/A   | see Assumptions |   identifier of the file   |
|  upload_timestamp |      TSWTZ      |    No    | curr ts |     Non     |      useful for logging        |
|   api_client_id   |      UUID       |    No    |   N/A   | Foreign Key | id of owner form clients table |

## 2. Design Decisions

### 2.1 Storage Reference
Why should the database store a storage key instead of an absolute filesystem path?
because the path might differ between systems, but a key can be consistent across all systems

### 2.2 Storage Providers
How will the schema support local filesystem and S3-compatible storage?
storage_configuration_id field will reference a storage configuration from a separated table that will hold the storage provider type and other configuration details

### 2.3 Client Isolation
How will the schema support isolating files belonging to different clients?
using api_client_id foreign key that will refer to a row in a separated api_clients table in my application

## 3. Assumptions

- api_client_id will refer to a row in a separated table for authenticated integrations(api_clients.id) which will hold the necessary information about the client.
- file_size_bytes should not allow null because I can extract the file size of any completed upload, and for uncompleted uploads, I won't store their metadata at all, 0 bytes files are permitted, the unique constraint on the storage_key field must have this composite unique constraint instead: UNIQUE (storage_configuration_id, storage_key), the upload_timestamp type should be like this: TIMESTAMP WITH TIME ZONE and its default is current timestamp(the timestamp of finishig the uploading process).
- I will use UUID Version 7: Time-Ordered Database Keys for the id field in this table and will be generated by the java code.
